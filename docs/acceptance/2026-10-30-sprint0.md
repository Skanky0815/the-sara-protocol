## Reproduzierbarer Ablauf

Aus einem Checkout des oben genannten Commits die unveränderte `compose.acceptance.yaml` verwenden. Vorher sicherstellen, dass das gewählte Projekt/Volume noch nicht existiert und Port 53043 frei ist. Ein eigenes temporäres Env-File mit Modus 0600 hält einen zufälligen, URL-sicheren Testwert für `POSTGRES_PASSWORD`; dieser Wert gehört nicht ins Repository.

```dotenv
BACKEND_IMAGE=ghcr.io/skanky0815/the-sara-protocol-backend@sha256:2561ea5dd84c1fbe748c3a6aad9c265cacb0ef5c6712318699da43e4e095deb0
POSTGRES_PASSWORD=EIGENER_ZUFAELLIGER_HEX_WERT
BACKEND_PORT=53043
```

Temporäre Override-Datei für den geprüften Migrationspfad und die feste Datenbankversion:

```yaml
services:
  backend:
    working_dir: /tmp
  postgres:
    image: postgres@sha256:31ba9c94a03ada9988f2bb493a22a75eef3a185884533e5cdbcd498ea835b08f
```

Im durchgeführten Lauf hießen die Dateien `/tmp/sara43.env` und `/tmp/sara43.override.yaml`, das Projekt `sara-sprint0-acceptance-20261030`. Für eine neue Wiederholung einen eigenen Projektnamen verwenden.

```sh
docker compose --env-file /tmp/sara43.env -p sara-sprint0-acceptance-20261030 \
  -f compose.acceptance.yaml -f /tmp/sara43.override.yaml pull
docker compose --env-file /tmp/sara43.env -p sara-sprint0-acceptance-20261030 \
  -f compose.acceptance.yaml -f /tmp/sara43.override.yaml \
  up --no-build --pull never -d --wait --wait-timeout 120
```

Die regulären Requests entsprechen [`backend/dev/persona.http`](../../backend/dev/persona.http), mit Basis-URL `http://127.0.0.1:53043`. Im Lauf wurden zwei Personas (`acceptance-alpha`, `acceptance-beta`) erstellt, ihre tatsächlichen IDs aus den Antworten übernommen und jeweils eine synthetische Memory angelegt. Bei Alpha wurde `2026-10-30T16:00:00+01:00` verwendet; die Antwort war `2026-10-30T15:00:00.000000Z`. Vor dem Neustart wurden vollständige Persona-/Memory-Antworten nur temporär gespeichert und nach dem Neustart exakt verglichen. Der Testtreiber war ein temporäres Python-Standardbibliothek-Skript; es wurde keine zweite Testautomatisierung eingeführt.

Beleg der leeren Datenbank und der Migrationen:

```sh
docker compose --env-file /tmp/sara43.env -p sara-sprint0-acceptance-20261030 \
  -f compose.acceptance.yaml -f /tmp/sara43.override.yaml exec -T postgres \
  psql -U sara -d sara -At -c \
  'SELECT version, success FROM _sqlx_migrations ORDER BY version; SELECT count(*) FROM personas; SELECT count(*) FROM memories;'
```

Vor den Requests: `20261027200000|t`, `20261028130000|t`, `0`, `0`. Backend-Ausgaben für `id -u`, `pwd` und `MIGRATIONS_DIR`: `10001`, `/tmp`, `/app/backend/migrations`.

Für den Persistenznachweis wurde der ganze Stack mit `down` ohne `--volumes` entfernt und mit dem obigen `up` erneut erstellt. Danach waren beide Personas und Memories vollständig identisch. Erst anschließend wurden die fehlerhaften Zeitstempel geprüft; sie sind deshalb nicht Teil des erfolgreichen Persistenz-Sollzustands.

### Blocker gezielt reproduzieren

Nur auf einer entbehrlichen Test-Persona verwenden: Der zweite Request kann deren Memory-Liste in diesem Image unlesbar machen.

```sh
# ID aus dem zuvor erfolgreichen POST /personas übernehmen:
PERSONA_ID=1
curl -i -H 'Content-Type: application/json' \
  -d '{"content":"synthetic boundary probe","source":"synthetic-boundary","observed_at":"2026-10-30","confirmation_status":"confirmed"}' \
  "http://127.0.0.1:53043/personas/$PERSONA_ID/memories"
curl -i -H 'Content-Type: application/json' \
  -d '{"content":"synthetic boundary probe","source":"synthetic-boundary","observed_at":"infinity","confirmation_status":"confirmed"}' \
  "http://127.0.0.1:53043/personas/$PERSONA_ID/memories"
curl -i "http://127.0.0.1:53043/personas/$PERSONA_ID/memories"
```

Tatsächlich beobachtet: erster Request 201; zweiter Request und anschließender Listenabruf schließen die Verbindung ohne HTTP-Antwort. In der isolierten Datenbank standen danach die Werte `2026-10-30 00:00:00+00` und `infinity`. Das Backend protokollierte `ColumnDecode` / `UnexpectedNullError` in `memories.rs` beim Auslesen von `observed_at`. Die Ablehnung muss vor dem Schreiben erfolgen; die Behandlung bereits gespeicherter Sonderwerte darf keine Task-Panic auslösen. Details und Regressionserwartungen stehen in #50.
